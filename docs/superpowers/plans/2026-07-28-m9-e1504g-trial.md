Host: e1504g (owner's working laptop, live niri session). All runs are
`dev/smoke-niri.sh` inside its own nested niri/dbus session, isolated
`HOME`/`XDG_*`, torn down after each screenshot. Host session and host
`org.freedesktop.Notifications` owner confirmed unchanged before/after each
run per the script's own assertion.

Repo at commit `1300b02` (pulled fresh at sweep start). Build: `nix build
.#formalshell --cores 4` (also re-run inside every smoke invocation itself,
near no-op after the first).

Real hardware present: `BAT0`/`AC0`, `intel_backlight`, live Wi-Fi (nmcli
shows active SSID), live Bluetooth (bluetoothctl lists nearby devices),
Intel/real GPU (not llvmpipe... TBD, confirm from debug dump / dmesg).

Screenshots pulled to `artifacts/e1504g/<mode>/` on the mac (gitignored;

## Results

This is part 1 of the sweep (9 of the plan's full mode list): plain, `--dump`,
`--wallpaper`, `--menu`, `--notify`, `--notify --center`, `--osd`,
`--clipboard`, `--media`. The remaining modes (`--lock`, `--screensaver`,
`--picker`, and the six `--panel` targets) are out of scope for this half and
left for the companion sweep.

### plain — PASS

`artifacts/e1504g/plain.png`. Bar renders correctly with real hardware
values: `BAT / 100%` cell (VM has no battery device at all, so
`docs/screenshots/bar-niri.png` never shows a BAT cell — this is the first
proof the UPower integration renders in the bar on real hardware, not just in
the power panel), volume `61%`, a filled Wi-Fi signal-strength glyph (VM shows
a disconnected/no-radio glyph), a Bluetooth glyph, and the static `WEATHER`
label cell (by design — `WeatherWidget.qml` always shows the literal text
"WEATHER" like Clock.qml's "TIME", it's an entry point, not a live reading;
confirmed by reading the widget source, not a defect). No title-case or
0..100 scaling defects visible in the bar text itself.

### --dump — PASS

`artifacts/e1504g/dump.png` (+ `dump-retry.png` from a second run). The
`debug dump` JSON is the first hard hardware proof:
`"brightness":{"available":true,"percent":100}` — VM dumps
(`artifacts/smoke-20260728-011648.json`, `-002628.json`) always report
`"available":false,"percent":0"` since there's no backlight device at all.
Audio volume `0.61` matches the bar's `61%` (0..1 scale rendered correctly,
not the earlier Wi-Fi 0..1 defect class). `configLoaded` includes the real
`location` lat/long the isolated settings.json seeds and the isolated
calendar `icsDir`.

One observation, not a defect: the first `--dump` run's screenshot
(`dump.png`) happened to land with the Weather panel open (`WEATHER /
LOADING`) and the cursor sitting on the Weather bar cell, even though
`--dump` never drives any click or panel-open IPC call. A second, identical
`--dump` run seconds later (`dump-retry.png`) shows the plain bar with no
panel and the cursor elsewhere. This isn't reproducible and there is no
hover-to-open code path in `WeatherWidget.qml`/`Panel.qml` (checked — only
`onClicked` toggles the panel), so the most plausible explanation is a real,
physical pointer event from the live host session leaking into the nested
winit window for one frame — something the fully synthetic VM (no physical
input device at all) can never produce. Flagged as a live-hardware sweep
caveat, not a shell bug: re-verify if it recurs.
