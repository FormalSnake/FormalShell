# M9 Task 3: e1504g real-hardware verification sweep

Host: e1504g (owner's working laptop, live niri session). All runs are
`dev/smoke-niri.sh` inside its own nested niri/dbus session, isolated
`HOME`/`XDG_*`, torn down after each screenshot. Host session and host
`org.freedesktop.Notifications` owner confirmed unchanged before/after each
run per the script's own assertion.

Repo at commit `1300b02` (pulled fresh at sweep start). Build: `nix build
.#formalshell --cores 4` (also re-run inside every smoke invocation itself,
near no-op after the first).

Real hardware present: `BAT0`/`AC0`, `intel_backlight`, live Wi-Fi (nmcli
shows active SSID), live Bluetooth (bluetoothctl lists nearby devices),
Intel/real GPU (not llvmpipe... TBD, confirm from debug dump / dmesg).

Screenshots pulled to `artifacts/e1504g/<mode>/` on the mac (gitignored;
this doc is the durable record).

## Results

This is part 1 of the sweep (9 of the plan's full mode list): plain, `--dump`,
`--wallpaper`, `--menu`, `--notify`, `--notify --center`, `--osd`,
`--clipboard`, `--media`. The remaining modes (`--lock`, `--screensaver`,
`--picker`, and the six `--panel` targets) are out of scope for this half and
left for the companion sweep.

### plain — PASS

`artifacts/e1504g/plain.png`. Bar renders correctly with real hardware
values: `BAT / 100%` cell (VM has no battery device at all, so
`docs/screenshots/bar-niri.png` never shows a BAT cell — this is the first
proof the UPower integration renders in the bar on real hardware, not just in
the power panel), volume `61%`, a filled Wi-Fi signal-strength glyph (VM shows
a disconnected/no-radio glyph), a Bluetooth glyph, and the static `WEATHER`
label cell (by design — `WeatherWidget.qml` always shows the literal text
"WEATHER" like Clock.qml's "TIME", it's an entry point, not a live reading;
confirmed by reading the widget source, not a defect). No title-case or
0..100 scaling defects visible in the bar text itself.

### --dump — PASS

`artifacts/e1504g/dump.png` (+ `dump-retry.png` from a second run). The
`debug dump` JSON is the first hard hardware proof:
`"brightness":{"available":true,"percent":100}` — VM dumps
(`artifacts/smoke-20260728-011648.json`, `-002628.json`) always report
`"available":false,"percent":0"` since there's no backlight device at all.
Audio volume `0.61` matches the bar's `61%` (0..1 scale rendered correctly,
not the earlier Wi-Fi 0..1 defect class). `configLoaded` includes the real
`location` lat/long the isolated settings.json seeds and the isolated
calendar `icsDir`.

One observation, not a defect: the first `--dump` run's screenshot
(`dump.png`) happened to land with the Weather panel open (`WEATHER /
LOADING`) and the cursor sitting on the Weather bar cell, even though
`--dump` never drives any click or panel-open IPC call. A second, identical
`--dump` run seconds later (`dump-retry.png`) shows the plain bar with no
panel and the cursor elsewhere. This isn't reproducible and there is no
hover-to-open code path in `WeatherWidget.qml`/`Panel.qml` (checked — only
`onClicked` toggles the panel), so the most plausible explanation is a real,
physical pointer event from the live host session leaking into the nested
winit window for one frame — something the fully synthetic VM (no physical
input device at all) can never produce. Flagged as a live-hardware sweep
caveat, not a shell bug: re-verify if it recurs.

### --osd — PASS with one defect found

Three artifacts: `artifacts/e1504g/osd-manual.png`, `osd-volume.png` (this
run's `smoke.png`/SMOKE_OK), `osd-brightness.png`.

`osd-manual.png` (manual `osd volume` IPC call): correct, `VOLUME 61%` card
with a proportionally-filled bar, matching the bar's own `61%` reading —
real hardware's actual system volume at sweep start.

`osd-brightness.png` (manual `osd brightness` IPC call): correct,
`BRIGHTNESS 100%` with a full bar — the real `intel_backlight` reading. The
VM's equivalent (`osd-niri.png` doesn't cover brightness, but `--dump`'s
`brightness.available:false` shows what the VM does instead) can only ever
render this kind as an honest empty 0%/unavailable card; e1504g is the
first real proof the populated-brightness path renders correctly.

**Defect:** `osd-volume.png`, the auto-show leg driven by a real `wpctl
set-volume @DEFAULT_AUDIO_SINK@ 30%` (not an IPC call — the actual
hardware-triggered path `AudioService.changed` is supposed to react to),
shows neither an updated bar nor an OSD popup — the bar still reads `61%`,
unchanged, and no volume OSD is visible at all. The VM's identical script
leg (`docs/screenshots/osd-niri.png`) correctly shows both the bar and the
OSD flipping to `30%` in the same timing window. A direct `wpctl
get-volume` on e1504g immediately after the run confirmed the real sink
had in fact changed to `0.30` and stayed there — so the volume change
itself took effect on the real hardware, but FormalShell's `AudioService`
never picked it up and re-rendered, across two screenshots roughly 1s and
5s after the change. This is a genuine defect specific to real audio
hardware (the VM's single null-sink graph apparently propagates the same
change fast enough; e1504g's real PipeWire graph — with a real hardware
sink, possibly more nodes/routing — does not update the shell's binding in
time, or at all, within the observed window). Restored the sink to its
original `61%` afterward (`wpctl set-volume @DEFAULT_AUDIO_SINK@ 0.61`) so
the sweep doesn't leave the owner's live session quieter than they left it.
Flagged for Task 4.

Separately (not a shell defect): both `osd-volume.png` and
`osd-brightness.png` show niri's own `Screenshot captured / You can paste
the image from the clipboard` toast in the top-right corner — real niri's
`screenshot-screen` action fires a desktop notification that the nested
session's own `NotificationServer` legitimately captures (since it owns
`org.freedesktop.Notifications` for that isolated bus), left over from the
`osd-manual.png` screenshot 5s earlier. The VM's screenshot never shows
this because the VM lacks whatever notification portal niri uses on real
hardware. Cosmetic overlap only, doesn't obscure the bottom-center OSD's
position.

## Summary (part 1 of 2)

8 of 9 modes in this half passed clean with no defects: plain, `--wallpaper`,
`--menu`, `--notify`, `--notify --center`, `--clipboard`, `--media`, and
`--dump`'s core JSON assertions. Every populated-hardware surface (BAT cell,
Wi-Fi/Bluetooth glyphs, real backlight percent, real MPRIS metadata) rendered
correctly and none of the previously-fixed defect classes (0..100 Wi-Fi
scaling, title-case UPower state) recurred anywhere in this sweep.

One real defect found: **`--osd`'s auto-show volume leg does not react to an
externally-driven volume change on real hardware** — `wpctl set-volume
@DEFAULT_AUDIO_SINK@ 30%` genuinely changed the system volume (confirmed via
a direct `wpctl get-volume` after the run) but neither the bar nor the OSD
picked it up within the run, across two screenshots ~1s and ~5s after the
change, while the VM's identical script leg updates both correctly in the
same window. Needs Task 4 investigation into `AudioService`'s reactivity to
externally-driven volume changes on a real PipeWire graph.

One non-defect observation: a single `--dump` run (not reproduced on retry)
screenshotted with the Weather panel open and the cursor over its bar cell,
despite `--dump` driving no click/panel IPC — most plausibly a stray real
pointer event from the live host leaking into the nested window for one
frame, something the fully-synthetic VM can never produce. Not chased
further; re-check if it recurs.

Remaining modes (`--lock`, `--screensaver`, `--picker`, and the six
`--panel` targets) are the companion sweep's scope, not covered here.
