### --osd — PASS with one defect found

Three artifacts: `artifacts/e1504g/osd-manual.png`, `osd-volume.png` (this
run's `smoke.png`/SMOKE_OK), `osd-brightness.png`.

`osd-manual.png` (manual `osd volume` IPC call): correct, `VOLUME 61%` card
with a proportionally-filled bar, matching the bar's own `61%` reading —
real hardware's actual system volume at sweep start.

`osd-brightness.png` (manual `osd brightness` IPC call): correct,
`BRIGHTNESS 100%` with a full bar — the real `intel_backlight` reading. The
VM's equivalent (`osd-niri.png` doesn't cover brightness, but `--dump`'s
`brightness.available:false` shows what the VM does instead) can only ever
render this kind as an honest empty 0%/unavailable card; e1504g is the
first real proof the populated-brightness path renders correctly.

**Defect:** `osd-volume.png`, the auto-show leg driven by a real `wpctl
set-volume @DEFAULT_AUDIO_SINK@ 30%` (not an IPC call — the actual
hardware-triggered path `AudioService.changed` is supposed to react to),
shows neither an updated bar nor an OSD popup — the bar still reads `61%`,
unchanged, and no volume OSD is visible at all. The VM's identical script
leg (`docs/screenshots/osd-niri.png`) correctly shows both the bar and the
OSD flipping to `30%` in the same timing window. A direct `wpctl
get-volume` on e1504g immediately after the run confirmed the real sink
had in fact changed to `0.30` and stayed there — so the volume change
itself took effect on the real hardware, but FormalShell's `AudioService`
never picked it up and re-rendered, across two screenshots roughly 1s and
5s after the change. This is a genuine defect specific to real audio
hardware (the VM's single null-sink graph apparently propagates the same
change fast enough; e1504g's real PipeWire graph — with a real hardware
sink, possibly more nodes/routing — does not update the shell's binding in
time, or at all, within the observed window). Restored the sink to its
original `61%` afterward (`wpctl set-volume @DEFAULT_AUDIO_SINK@ 0.61`) so
the sweep doesn't leave the owner's live session quieter than they left it.
Flagged for Task 4.

Separately (not a shell defect): both `osd-volume.png` and
`osd-brightness.png` show niri's own `Screenshot captured / You can paste
the image from the clipboard` toast in the top-right corner — real niri's
`screenshot-screen` action fires a desktop notification that the nested
session's own `NotificationServer` legitimately captures (since it owns
`org.freedesktop.Notifications` for that isolated bus), left over from the
`osd-manual.png` screenshot 5s earlier. The VM's screenshot never shows
this because the VM lacks whatever notification portal niri uses on real
hardware. Cosmetic overlap only, doesn't obscure the bottom-center OSD's
position.

### `--lock` — environment-blocked, not a shell defect

Three screenshots pulled: `artifacts/e1504g/lock-locked.png`,
`lock-error.png`, `lock-unlocked.png`. The script itself exited
`SMOKE_FAIL: lock isLocked did not flip back to false after the real
password — got: true`.

Root cause confirmed by reading `Lock.qml` and checking the host directly:
`PamContext { config: "formalshell-lock" }` authenticates against
`/etc/pam.d/formalshell-lock`, a service file `nixosModules.formalshell`
declares (`nix/testvm.nix:101`, `services.formalshell.enable = true`, is
where the VM gets it). `ls -la /etc/pam.d/formalshell-lock` on e1504g
confirms it does **not exist** there — expected, since e1504g's system has
not been switched onto the nixosModule yet (that switchover is exactly
Task 5's gate, not yet crossed). `Lock.qml:172-189`'s own comment
documents this exact failure mode: `pam.start()` returns false when the
named PAM service is missing, and the code deliberately surfaces
`"PAM ERROR"` rather than hanging silently. Both `lock-error.png` (after
the deliberately wrong `wtype "wrong-password"`) and `lock-unlocked.png`
(after `wtype`-ing the VM-only fixture password `"formalshell-test"`, which
was never going to match e1504g's real account password either) show the
identical uppercase `PAM ERROR` meta row rather than `WRONG PASSWORD` —
correct given neither attempt could even start a PAM conversation, and the
screen correctly stayed locked (fails closed) both times.

What this half DOES prove on real hardware: the surface renders correctly
(oversized clock, bordered input cell, uppercase error meta row exactly per
`docs/screenshots/lock-niri.png`'s layout), the lock command and
`isLocked:true` round-trip correctly, and the screen never unlocks without
successful PAM auth — the security-critical fail-closed behavior holds.
What it can NOT prove here: the actual password-correct (`PamResult.Success`)
and password-wrong (`PamResult.Failed` → `"WRONG PASSWORD"`) paths, since
both require the `formalshell-lock` PAM service that only exists once the
nixosModule is switched in. Not re-attempted with a guessed real password —
that would mean touching the owner's actual login credential, out of scope
for this task. Record this as a known gap for Task 5's parity table: `--lock`
on e1504g is verified for locking/error-rendering/fail-closed only, the
correct-password path remains VM-only verified until switchover.

### `--panel audio` — DEFECT found

`artifacts/e1504g/panel-audio.png`. Real hardware exposes six real Pipewire
nodes instead of the VM's single `Virtual Sink` — `Easy Effects Sink` at
`100%` (percentage renders correctly) plus five real `Alder Lake-M PCH High
Definition Aud[io …]` output/input devices, none of which show a percentage
at all next to their name (confirmed by cropping and zooming the row: the
name runs straight into the `MUTE` button with no `NN%` anywhere).

Root cause, read directly from `AudioPanel.qml:42-50`: the row's `Text`
builds `(description || name) + "  " + round(volume*100) + "%"` as one
string, on a fixed-width `Text` with `elide: Text.ElideRight`. Because the
percentage is appended at the very end of the string, any device name long
enough to need eliding (every real Alder Lake ALSA description — the VM's
short `"Virtual Sink"` never hit this) truncates the percentage away first,
before the name itself is even fully cut. The fader bar below each row
still fills to the correct proportion, so the *data* is fine — only the
percentage's on-screen text is lost for any long-named device. This is a
real, reproducible defect specific to real hardware's naturally longer
device descriptions; flagged for Task 4 (put the percentage before the name,
or reserve fixed trailing width for it so elision never eats it).

## Summary (part 2 of 2)

6 of 9 modes in this half are clean passes with no defect: `--screensaver`,
`--picker`, `--panel network`, `--panel power`, `--panel calendar`,
`--panel media`. `--lock` is environment-blocked rather than a shell defect
— e1504g has not been switched onto `nixosModules.formalshell` yet, so the
`formalshell-lock` PAM service the lock screen authenticates against does
not exist there, and the render/fail-closed/lock-command contract is
proven while the actual password-correct/password-wrong paths remain
VM-only verified until switchover (Task 5's parity table should say so
plainly).

Two real defects found, both in the `--panel` half where real device names
first appear:

1. **`AudioPanel.qml`'s per-device row text loses its volume percentage for
   any device name long enough to trigger `elide: Text.ElideRight`** — every
   real Alder Lake Pipewire node hits this (the VM's short `"Virtual Sink"`
   never did), because the percentage is appended at the very end of the
   single elided string.
2. **`BluetoothPanel.qml`'s adapter-state text is not uppercased** —
   `BluetoothAdapterState.toString(...)` renders `"Enabled"` instead of
   `"ENABLED"`, the same defect class as the already-fixed `UPowerDeviceState`
   title-case bug, but at a call site that fix didn't cover. Every other
   `.toString(` call site under `shell/Surfaces/Panels/` was grepped and
   confirmed to already call `.toUpperCase()` correctly.

Both are flagged for Task 4, alongside part 1's `--osd` auto-show
reactivity defect.
