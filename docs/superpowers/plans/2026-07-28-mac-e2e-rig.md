## Architecture (researched on this macbook 2026-07-28, not assumed)

Established facts this design rests on:

- The mac runs **Determinate Nix 3.21.0** under nix-darwin with
  `determinateNix.enable = true`, which *disables nix-darwin's own `nix.*`
  management*. So nix-darwin's `nix.linux-builder.enable` is **not**
  available — do not burn time on it.
- `/etc/nix/nix.conf` (Determinate-managed) already contains
  `builders = @/etc/nix/machines`, and `/etc/nix/machines` does not exist.
  Creating that file is all the mac's nix daemon needs to offload
  aarch64-linux builds. `trusted-users = root` only gates *client-supplied*
  settings; the daemon reads `builders` itself, so no trusted-users change
  is required.
- `nix build nixpkgs#darwin.linux-builder` is **fully substitutable** on this
  host (`561 paths will be fetched`, 397 MiB) — the bootstrap builder needs
  no pre-existing linux builder. `nixpkgs#qemu` for aarch64-darwin is also
  fully substitutable (20 paths).
- Hardware: Apple M1 Pro, 10 cores, 32 GiB RAM, `kern.hv_support = 1` (HVF).
  `sudo` is passwordless on this host.
- `nixos/modules/profiles/nix-builder-vm.nix` in the pinned nixpkgs is the
  proof that **a NixOS VM whose runner script is a darwin package works**:
  it sets `virtualisation.host.pkgs` to the darwin pkgs, `useNixStoreImage`,
  `writableStore`, `forwardPorts`, `graphics = false`, and exposes
  `config.system.build.vm` as a darwin-runnable script. `qemu-vm.nix` in the
  same tree provides `virtualisation.sharedDirectories` (9p `-virtfs`),
  `virtualisation.cores`, `virtualisation.host.pkgs`. Our testvm is that same
  mechanism with our own guest config — read both files before writing any
  nix.

Two layers:

1. **Build layer** — the stock `darwin.linux-builder` VM, kept alive in the
   background and registered in `/etc/nix/machines`, so
   `nix build .#packages.aarch64-linux.<x>` works from the mac. Its only job
   is building the testvm closure (and giving `just build` a real meaning on
   darwin). Bootstrap with the **default** config: any override of
   `diskSize`/guest-side options makes linux derivations non-substitutable
   and re-creates the chicken-and-egg. `memorySize`/`cores` overrides only
   touch the darwin runner script — verify with `nix build --dry-run` before
   relying on that.
2. **Runtime layer** — `nixosConfigurations.testvm` in **this** repo, run by
   `packages.aarch64-darwin.testvm = …config.system.build.vm`, booted
   headless with HVF. Inside it:
   - a **headless wlroots parent compositor** (sway, `WLR_BACKENDS=headless`,
     `WLR_RENDERER=pixman`) as a systemd **user** service, publishing
     `WAYLAND_DISPLAY` into the systemd user environment exactly like
     niri-session does on the g815;
   - the existing `dev/smoke-*.sh` scripts run **unchanged** inside, nesting
     their own niri as a winit client of that parent, with their own
     `dbus-run-session` + isolated `HOME`/`XDG_*` — which keeps them
     bit-compatible with the Linux hosts.

   **Why headless-parent instead of niri on a virtio-gpu DRM device (a
   deliberate deviation from the earlier draft's preference order):** the
   smoke scripts are *nested by design* — they hard-require a parent
   `WAYLAND_DISPLAY` and fail with `SMOKE_FAIL` without one. A DRM session in
   the guest would add a GPU/seat dependency without changing one byte of
   what gets tested. Software rendering (Mesa llvmpipe for the nested niri's
   EGL, pixman for the parent) is the only concession, and it is the same
   concession CI-grade wlroots testing makes everywhere. Record this
   trade-off in the docs task.

   The guest's store image is built by layer 1, so it can **pre-stage** the
   expensive closures: put `self.packages.aarch64-linux.formalshell`,
   quickshell, `qt6.qtdeclarative`, matugen, niri and sway in
   `environment.systemPackages`. `nix build .#formalshell` inside the VM then
   finds quickshell already present and only ever rebuilds formalshell's own
   small derivation as the source changes — the edit→smoke loop stays fast
   without a shared store.

**Driver:** `dev/vm.sh` with `start` (boot headless in background, wait for
ssh), `stop`, `status`, `sync` (push the working tree into the VM — the repo
is what gets tested, not a commit), `run <cmd…>` (ssh, cwd = the repo inside
the VM, session env set up: `WAYLAND_DISPLAY`, `XDG_RUNTIME_DIR`,
`DBUS_SESSION_BUS_ADDRESS`), `smoke <flags…>` (run `dev/smoke-niri.sh` in the
VM, then pull the produced PNG/JSON to `./artifacts/` and print mac-local
paths). `justfile` gains `vm-up`, `vm-down`, `vm-build`, `vm-test`, `vm-lint`,
`vm-smoke *FLAGS`.

## Plan-wide constraints

- All `CLAUDE.md` hard rules hold. The VM replaces "nested session on the
  g815" as the isolation boundary; inside it, the existing scripts still do
  their own HOME/XDG + `dbus-run-session` isolation, so they stay portable
  back to the Linux hosts.
- **No changes to `shell/` source in this plan** — rig only. The smoke
  scripts may gain VM-awareness only if it is strictly additive and keeps
  Linux-host behaviour identical; prefer changing nothing in them.
- Screenshots must land on the **mac** filesystem under `./artifacts/`
  (gitignored) and be Read-verified in the workflow — same standard as
  before. `docs/screenshots/*.png` is only updated by a docs task that Reads
  the image first.
- CI stays linux-x86_64 (GitHub runners) — **do not couple CI to the VM**.
- Both Linux hosts (g815, e1504g) are OFFLINE. Never attempt ssh to them.
- Changes to the owner's nix config repo (`~/.config/nix`) are pre-approved
  for this rig but must be minimal, committed in that repo (its own
  `CLAUDE.md` applies), and must not alter unrelated host behaviour. Prefer
  the zero-rebuild route (`/etc/nix/machines`) and only escalate to a
  `darwin-rebuild` if the zero-rebuild route provably cannot work.
- Long builds are expected (Qt/quickshell for aarch64-linux inside a 1-vCPU
  QEMU guest). Use generous `timeout` values or background the command and
  poll — do not conclude "broken" from a harness timeout.
- Commit/push per task. Every task ends with its verification commands
  actually run and their output read.

### Task 1: aarch64-linux build capability from the mac

**Files:** create `dev/linux-builder.sh`; modify `.gitignore`.

**Produces:** a `dev/linux-builder.sh` with `start` (boot the stock
`darwin.linux-builder` in the background, wait until ssh answers), `stop`,
`status`, and `register` (idempotently write `/etc/nix/machines` and the
matching ssh client config, via `sudo`). Keys and the VM's qcow2 live in a
gitignored `dev/.linux-builder/` working directory (the profile's
`add-keys`/`create-builder` scripts generate the keypair and `sudo`-install
the private key to `/etc/nix/builder_ed25519` themselves — read
`nixos/modules/profiles/nix-builder-vm.nix` in the pinned nixpkgs and mirror
what it actually does; the `KEYS` env var and `virtualisation.darwin-builder.workingDirectory`
are the levers).

For the exact `/etc/nix/machines` line format (protocol, system, key path,
maxJobs, speed factor, system-features, mandatory-features, base64 host
public key) and the ssh-config stanza, read nix-darwin's own
`modules/nix/linux-builder.nix` — it is available in the store via the
owner's config flake (`~/.config/nix`, input `nix-darwin`/`darwin`). Do not
invent the format.

**Steps:** start the builder → register → from the repo run
`nix build --no-link --print-out-paths .#packages.aarch64-linux.formalshell`
→ confirm the store path is aarch64-linux (`nix path-info --json` / a
`file` on a binary inside it) → re-run to show it is a no-op → `dev/linux-builder.sh stop`
then `start` again to prove the persistence of the qcow2 and registration →
commit `feat(dev): aarch64-linux builder bootstrap for the macbook`; push.

**Evidence required:** the printed store path, the second (cached) run, and
the exact `/etc/nix/machines` content. If resources bite (OOM/disk during the
build), escalate exactly once by overriding `memorySize`/`cores` on the
builder and prove with `nix build --dry-run` that the override rebuilds only
darwin-side paths — then record it in the script.

### Task 2: `nixosConfigurations.testvm` boots headless with ssh

**Files:** create `nix/testvm.nix`; modify `flake.nix`, `.gitignore`.

**Produces:** `nixosConfigurations.testvm` (aarch64-linux) and
`packages.aarch64-darwin.testvm = self.nixosConfigurations.testvm.config.system.build.vm`.
Guest configuration, all of it verified against `qemu-vm.nix` /
`nix-builder-vm.nix` rather than guessed:

- `virtualisation.host.pkgs = nixpkgs.legacyPackages.aarch64-darwin`,
  `graphics = false`, `cores` ≈ 6, `memorySize` ≈ 8192, `diskSize` ≈ 40960,
  `useNixStoreImage = true`, `writableStore = true`,
  `writableStoreUseTmpfs = false`, `useHostCerts = true`,
  `forwardPorts` host 2222 → guest 22.
- `networking.nameservers = [ "8.8.8.8" ]` — QEMU SLiRP's own DNS is broken
  on macOS (the upstream profile documents this; without it the guest cannot
  reach `cache.nixos.org`).
- A normal user `test` (uid 1000) with password-less sudo, getty autologin,
  `services.openssh.enable` with an authorized key; the keypair is generated
  by `dev/vm.sh` into a gitignored `dev/.testvm/` and passed in the same way
  the upstream profile passes its keys (a shared directory), so the flake
  contains no secret and no host-specific path.
- `virtualisation.sharedDirectories` — decide between a 9p share of the repo
  and `dev/vm.sh sync` (rsync over ssh) in **Task 4**; this task only needs
  to boot. If a 9p share is wired here, it must tolerate the source
  directory being absent.
- Guest packages (pre-staging the closure so in-VM builds are cheap):
  `self.packages.aarch64-linux.formalshell`, quickshell, `qt6.qtdeclarative`,
  matugen, niri, sway, imagemagick, libnotify, brightnessctl, wireplumber,
  git, just, iproute2, jq, bash, plus `services.pipewire` (with pulse) and a
  Nerd Font in `fonts.packages` with fontconfig enabled.
- `hardware.graphics.enable = true` (Mesa/llvmpipe for the nested niri's
  EGL), `security.polkit.enable`, `nix.settings.experimental-features`,
  `nix.settings.trusted-users = [ "test" ]`, `system.stateVersion`.

**Steps:** `git add -A && nix build .#testvm` on the mac (offloaded to the
Task-1 builder) → boot it in the background → `ssh -p 2222 test@localhost 'uname -m; nixos-version; systemctl is-system-running'`
→ `nix build .#formalshell` inside the VM must be a **no-op** (proving the
pre-staging works) → shut down cleanly → commit
`feat(nix): headless aarch64 nixos test vm for mac e2e`; push.

### Task 3: headless wayland parent session inside the VM

**Files:** modify `nix/testvm.nix`.

**Produces:** a systemd **user** service (e.g. `testhost-compositor.service`,
`WantedBy=default.target`) running sway with `WLR_BACKENDS=headless`,
`WLR_RENDERER=pixman`, `WLR_LIBINPUT_NO_DEVICES=1` and a minimal generated
config whose only job is `exec systemctl --user import-environment WAYLAND_DISPLAY DISPLAY`
(plus `systemctl --user set-environment`), so that
`systemctl --user show-environment | grep WAYLAND_DISPLAY` answers inside the
VM — the exact lookup `dev/smoke-niri.sh` falls back to. A `linger` setting
(`users.users.test.linger = true`) so the user session exists without an
interactive login, and `XDG_RUNTIME_DIR`/`DBUS_SESSION_BUS_ADDRESS` reachable
over plain ssh.

**Steps (all over ssh from the mac):**
- `swaymsg -t get_outputs` shows a HEADLESS output.
- `ss -xl` lists the parent's wayland socket (the liveness check
  `dev/smoke-niri.sh` uses).
- `busctl --user status org.freedesktop.Notifications` answers (empty owner
  is fine — it must not error, because the smoke script's host-bus assertion
  depends on it being a real query).
- Nested niri actually runs: launch `niri --config <minimal>` under the
  parent with a `spawn-at-startup` that runs `niri msg outputs` into a file,
  and read that file back.
- commit `feat(nix): headless wlroots parent session in the test vm`; push.

**If nested niri cannot get an EGL context after 3 distinct approaches**
(llvmpipe env vars, `LIBGL_ALWAYS_SOFTWARE`, a different parent compositor):
report `blocked` with the exact niri stderr. Do **not** downgrade to "unit
tests only".

### Task 4: `dev/vm.sh` + just recipes

**Files:** create `dev/vm.sh`; modify `justfile`, `.gitignore`.

**Produces:** `dev/vm.sh` — `start` (build if needed, boot in background,
generate the ssh key on first run, wait for ssh with a bounded loop and a
clear failure message), `stop` (graceful `poweroff` then a fallback kill),
`status`, `sync` (push the **working tree** into `/home/test/formalshell`
inside the VM — `rsync -a --delete` over ssh, excluding `result*`,
`.git/index.lock`, `artifacts/`; the working tree is what gets tested),
`run <cmd…>` (ssh with the session env exported and cwd at the repo),
`smoke [flags…]` (sync, run `dev/smoke-niri.sh` with the flags inside, parse
the `SMOKE_OK <path>` line, `scp` that PNG plus any JSON the mode printed
into `./artifacts/`, and print the mac-local paths), `shell` (interactive
ssh). Never touches the host's `NIRI_SOCKET`/`HYPRLAND_INSTANCE_SIGNATURE` —
on darwin there are none, but the script must still not invent any.

`justfile`: `vm-up`, `vm-down`, `vm-build` (`nix build .#formalshell` in the
VM), `vm-test` (qmltestrunner in the VM), `vm-lint`
(`git add -A` + `nix flake check -L` in the VM), `vm-smoke *FLAGS`. Keep the
existing darwin-native `test` recipe as is.

**Steps:** `just vm-up` → `just vm-build` (store path printed) →
`just vm-test` (80 passed, 0 failed) → `just vm-lint` (qml-tests + qmllint
both pass for aarch64-linux) → `just vm-down` → `just vm-up` again to prove
idempotence → commit `feat(dev): vm.sh driver and vm-* just recipes`; push.
